## 背景

- **现状**：现在是什么行为，谁受影响（用户 / 某个模块 / 某条流水线）。
- **为什么要改**：问题现象、触发条件、影响范围；能贴证据就贴（日志片段、报错原文、截图链接）。
- **不做什么**：这次刻意不碰的范围，免得审查人按「应该顺带修」来要求。

## 改动点

- 按模块分条，**一条一件事**；说清「改了什么」和「为什么这么改」，不要复述 diff。
- 涉及接口 / 参数 / 配置 / 数据结构的改动，把新旧口径并列写出来（旧 → 新）。
- 顺手做的清理单独列一行，标注「顺带」，方便审查人决定要不要拆 PR。

## 怎么验证

给审查人一份**能照着做**的清单：命令、入口、预期结果。分三档，没有的写「不适用」。

1. **自动**：`<测试 / 构建命令>` —— 预期全绿。
2. **手动**：从哪进 → 点什么 → 看到什么（给具体页面路径或接口 + 期望响应）。
3. **边界**：空值、超大输入、并发、无权限、网络失败这些踩过的坑各测了什么。

- [ ] 关键路径走通
- [ ] 失败路径有可读报错，不是静默
- [ ] 没验证的部分：<写清楚哪些没测、为什么>

## 风险与回滚

- **风险等级**：低 / 中 / 高（高 = 影响线上数据、权限、不可逆操作）。
- **影响面**：哪些调用方 / 哪些环境 / 是否需要同步发版。
- **回滚方式**：`git revert <sha>` 即可 / 需要关开关 `<配置键>` / 需要回滚数据（写清脚本）。
- **上线顺序**：有没有必须先上的依赖（迁移、配置、别的服务）。

## 关联工作项

- 关联工作项：`<项目 / ident>`（也可以建完 PR 后在详情里关联，别只写在描述里）
- 依赖 / 被依赖的 PR：`#<iid>`（同一批改动拆了几个 PR 时列全，标清合并顺序）
- 后续待办：这次不做、但必须有人接着做的事（写清由谁跟进）
